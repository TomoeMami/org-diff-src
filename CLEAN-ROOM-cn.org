本文档面向希望独立实现相同用户可见行为的开发者：可以为 Emacs、为 Org，
也可以为其他编辑器实现，而不复制本包的代码或文字。它借用 GNU 和其他自由
软件项目长期使用的净室方法：一组人只根据公开文档和可观察行为整理规格；
另一组人只根据这份规格编写实现。

规格会详细说明问题、约束和必须满足的行为，但会有意省略实现机制。它不包含
代码、函数名或变量名、数据结构、正则表达式，也不包含按步骤操作的配方。这些
选择属于独立实现者。主 [[file:README-cn.org][README]] 记录的是本包的具体实现；如果要做严格的
净室流程，只使用本文档、Emacs 与 Org 的公开文档，以及黑盒观察。

当实现由 AI 辅助完成时，同样的纪律仍然适用。本文档被写成自包含的规格，可以
作为唯一的项目相关输入；不要要求助手根据记忆或源码“还原”本包。下面的 AI
辅助开发部分也给出了一套可操作的 AI 使用规范。

需要说明的是，本文档不是法律意见，也不能替代真正的双团队净室记录。它提供的
是一个行为规格模板；如果你的场景需要可举证的法律意义上的净室过程，应由未
接触源码的人独立整理规格，并保存实验、评审和沟通记录。

* 问题与核心约束

Org 可以在源码块中显示 unified diff，但这样显示的 diff 往往会丢失编辑器
内置 diff 模式在独立缓冲区中提供的细粒度 refinement（细化）。用户能看到
整行的新增和删除，却看不到具体哪些字词发生了变化、词内哪些字符不同。任务
就是把这个区分恢复到 Org 缓冲区本身，不启动 Ediff 会话，也不要求 Org 和
编辑器内置 diff 支持之外的包。

真正困难的部分不是解析 unified diff，而是理解 Org 如何把源码块文本变成
显示文本，并选择一种能穿过这条路径的细化表示。

一个需要独立验证的核心约束是：Org 并不是简单地在 Org 缓冲区里对源码块文本
运行某个主模式；它会在一个间接的上下文中准备显示，再把结果的一部分传回 Org
缓冲区。这个传递是有损的，有些显示信息能保留，有些不能。一个在独立缓冲区里
看起来完美的细化，放进 Org 后可能完全消失。

这是应该最先调查的约束，也是独立实现者应该自己发现的部分。通用策略是：

- 把字体化边界当成一份契约。通过 Org 中的公开实验，确定哪些显示表示能穿过
  这个边界、哪些不能，并记录实验和结果。
- 选择一种落在能够穿过边界的子集内的细化表示，并把细化计算安排在这种表示
  能够产生的位置。
- 把 diff 解析器和细化渲染器分开。解析器决定哪些行是新增、删除或上下文，
  以及一行中哪些范围对应哪一侧；渲染器把这些范围变成显示属性。两者可以在
  不重写对方的情况下替换。
- 在合适的时候复用编辑器已有的 diff 解析和行级高亮。从零写解析器也可以，
  但它不是这个功能的价值所在，而且更容易产生行为偏差。
- 对你依赖的编辑器私有行为保留一层隔离，使未来的版本可以退回行级显示。优先
  使用公开、有文档的接口；把私有接口当作可选的加速手段，而不是地基。
- 在目标缓冲区中、经过正常的字体化路径之后再验证，而不是在计算细化的临时
  缓冲区里验证。

存在不止一种有效设计。规格要求的是可见结果，而不是某一种机制。

* 概念结构

一种有用的分层是：

1. 生产者：把输入变成 unified diff 文本。
2. 插入器：把这段文本包装成源码块并放进 Org 缓冲区。
3. 细化器：计算发生变化的范围及其显示方式。
4. 集成层：让插入器和细化器满足字体化边界的要求。

生产者层必须可替换；细化层不需要知道文本来自哪里；只有集成层需要了解 Org
的字体化行为。这样可以把净室边界收得很小，也让测试更集中。

* 必须满足的行为

符合规格的实现应满足以下可观察要求。它们按验收标准书写，而不是按设计书写。

1. *渲染：*
   插入 Org 缓冲区的 unified diff 显示为 Org 源码块。新增、删除
   和上下文行得到通常的行级 diff 处理。在发生变化的行内，发生变化的字词
   以及词内不同的字符与未变化的文本在视觉上可区分。
2. *持久性：*
   经过正常字体化后，细化结果存在于 Org 缓冲区中；源码块被编辑并
   再次字体化后，结果能够恢复。它不能依赖某个临时缓冲区继续存活。
3. *来源：*
   同一条渲染路径接受来自独立生产者的 diff：两个字符串、两个文件、
   两个缓冲区、两个 Org 子树、已有的 diff 文件、当前区域和 kill ring。
   生产者只需提供合法的 unified diff 文本，不需要知道细化如何渲染。
4. *没有隐藏会话：*
   渲染不会启动 Ediff、创建新 frame，或留下多余窗口和
   缓冲区。命令返回前，临时窗口变化应被恢复。
5. *不影响剪贴板与 kill ring：*
   比较或渲染 diff 不得改变 kill ring、yank
   指针或系统剪贴板。从 kill ring 读取是允许的，写入不是。
6. *不修改文件：*
   比较文件只读取文件；远程文件的临时副本会被清理。
7. *空输入：*
   空 diff 产生一个有明确说明的占位文本，而不是报错或空块。
8. *格式容忍：*
   unified diff 会被细化；其他 diff 格式和畸形输入以文本形式
   显示，不报错。细化失败不能让源码块变得不可读。
9. *旧名称：*
   用户可以把已有的源码块语言名映射到新的渲染器。注册别名不得
   改变无关源码块的行为；把 =diff= 这类通用名称映射进来必须是显式选择。
10. *优雅降级：*
    如果编辑器改变了细化所依赖的内部行为，源码块仍能以行级
    高亮工作。降级应在渲染时决定，而不是在加载时直接失败。
11. *开销：*
    渲染时间和内存随 diff 大小和变化区域增长。很大的 diff 可以
    比较慢，但渲染被中断后缓冲区必须仍然有效，重试时不能重复叠加 face。
12. *导出：*
    diff 文本属于文档并正常导出。细化颜色是显示属性；实现不必在
    HTML 或 PDF 导出中保留颜色，但不得破坏导出的文本。

* 有意省略的内容

这份规格不说明：

- 使用哪些 Org 或 diff 模式的平台接口、内部 hook 或数据结构；
- 细化由哪一种显示机制承载；
- 显示信息如何穿过字体化边界；
- 解析算法、正则表达式或数据结构；
- 命令名、自定义项名、源码块分隔符或错误消息；
- 文件布局、实现顺序或测试数据。

这些都是实现选择。如果一个行为必须点名某个私有机制才能测试，它多半被描述
在了错误的层次上；请把它改写成用户能够观察到的结果。

* 独立验证

- 在编写实现之前，先根据本文档写出验收测试。
- 只通过公开命令驱动，经过正常字体化后检查 Org 缓冲区。
- 断言位置、可见文本和 face 属性；不要断言临时缓冲区、内部显示对象或私有
  变量。
- 至少覆盖：空 diff、单字符变化、整行替换、新增和删除文件、二进制 diff、
  CRLF、非 ASCII、超长行、末尾缺少换行、畸形的 hunk 头。
- 在每条命令执行前后，快照 kill ring、剪贴板、缓冲区列表、窗口配置和文件
  修改时间。
- 在支持的最旧和最新 Emacs 上运行测试；使用干净的 init，并分别测试开启和
  关闭 font-lock 的情况。关闭 font-lock 时，即使没有细化，源码块也必须可读。
- 不要复制本仓库的测试；它们属于实现，可能编码了具体机制。

* AI 辅助开发

AI 助手可以在两个“房间”里发挥作用，但不能成为两个房间之间的通道。

- 在规格房间中，AI 可以总结公开手册、发布说明、bug 报告和可观察行为，并
  帮助把它们变成需求和测试想法。不要给它原始源码、注释或本仓库的实现章节，
  也不要让它“还原”本包。
- 在实现房间中，只给助手冻结后的规格和公开的平台文档。本文档就是为这个用途
  写成自包含的规格。
- 保留来源记录：提示词、模型与版本、日期和输出。除了正确性，还要审查输出
  与原始实现的相似度。相似度是证据，不是证明；看起来像是派生自原实现的
  部分应当重写。
- 按照项目的记录惯例披露 AI 参与，例如使用 =Assisted-by= 提交尾注。披露
  不转移责任：必须由具名的人类维护者评审并接受结果。
- 不要假设模型输出不附带第三方义务。在某些司法辖区，纯 AI 生成的材料可能
  不受版权保护，或者作者身份不确定；人类的挑选、编排和修改才是可依赖的
  部分。保留模型服务的条款记录，并让具名的人类承担责任。
- 如果模型训练时见过原始仓库，它的输出不会自动成为复制品，但风险更高。优先
  使用只基于规格的提示词，并审计结果。
- 如果法律或平台政策要求标识 AI 生成内容，应遵守这些要求；提交尾注和发布
  说明是一个合理的起点。

对 Emacs 和 Org 本身的 AI 辅助贡献，这也是合理的默认做法：描述行为、披露
工具、审查 diff、保留记录。

* 许可证边界

- 版权保护表达，不保护思想、方法或功能行为。净室开发是独立创作的证据，不是
  普遍的法律护盾；具体分析因司法辖区而异。
- 独立实现如果没有复制本包的代码、注释或文字，可以由作者自行选择许可证。
  如果复制或改编了本仓库的代码或文字，GPL-3.0-or-later 适用于被复制的部分，
  并可能影响组合作品。
- 兼容并不要求复用本包的名称或接口。请选择你自己的名称；提到本包时，把它
  当作先前工作，而不是背书。
- 专利、商标和商业秘密不在本文档的讨论范围内。用于商业或高风险场景时，请
  咨询律师。

* 把模式用到别处

同样的推理适用于任何想在源码块中获得丰富显示的 Emacs 或 Org 功能：找出
字体化边界，发现可传递的子集，把生产者和渲染器分开，提供降级路径，并在
目标缓冲区中测试。diff 细化只是其中一个实例；行内注释、语法感知的折叠、
外部数据预览都是别的实例。净室方法与具体功能无关。
